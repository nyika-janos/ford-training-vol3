# Day 1 - Exercise 6

# Connect Cloud Storage to Pub/Sub

## Objective

Create a Cloud Storage notification that publishes a Pub/Sub message whenever a new file is uploaded to the **landing** folder of your bucket.

By the end of this exercise, the following flow will work:

```text
Excel
   ↓
Cloud Storage (landing/)
   ↓
Pub/Sub Topic
   ↓
Subscription
   ↓
Message
```

15 minutes

## Background

Cloud Storage can generate events whenever something happens inside a bucket.

Examples:

- A new file is uploaded
- A file is deleted
- Object metadata is updated

Today we will use the following event:

```text
OBJECT_FINALIZE
```

This event occurs whenever a new object is successfully created in the bucket.

Historically, notification configurations could be created directly from the Cloud Storage user interface. Today, many teams manage them through the Google Cloud CLI.

The goal of this exercise is to understand how an event generated by Cloud Storage can be published into Pub/Sub.

In real-world data platforms we usually do not generate events for every object in a bucket.

Instead, notifications are often restricted to specific areas of the storage hierarchy.

In this training we only want to react to files arriving in:

```text
landing/
```

Files uploaded to:

```text
archive/
error/
export/
```

should not trigger a new ingestion process.

This mirrors a common enterprise data platform design pattern.

Additional documentation:

Cloud Storage Pub/Sub Notifications:

https://docs.cloud.google.com/storage/docs/pubsub-notifications

gcloud notification commands:

https://docs.cloud.google.com/sdk/gcloud/reference/storage/buckets/notifications

## Step 3

Create the notification configuration.

Replace:

```text
A_TE_BUCKET_NEVED
```

with your bucket name.

Replace:

```text
A_TE_PUB_SUB_TOPIC_NEVED
```

with your topic name.

Run:

```bash
gcloud storage buckets notifications create gs://A_TE_BUCKET_NEVED \
  --topic=A_TE_PUB_SUB_TOPIC_NEVED \
  --event-types=OBJECT_FINALIZE \
  --object-prefix=landing/
```

Example:

```bash
gcloud storage buckets notifications create gs://training-janos \
  --topic=file-arrived-topic-janos \
  --event-types=OBJECT_FINALIZE \
  --object-prefix=landing/
```

The additional parameter:

```text
--object-prefix=landing/
```

ensures that notifications are generated only for objects uploaded into the landing folder.

Files uploaded elsewhere in the bucket will not generate events.

Expected output:

```text
Created notification config ...
```

## What Happens Next?

Today we manually inspect the message.

On Day 3 the same event will trigger a Cloud Run service.

On Day 4 the same event can trigger a Composer / Airflow workflow.

The event remains the same.

Only the consumer changes.

```text
Day 1:
Bucket → Pub/Sub

Day 3:
Bucket → Pub/Sub → Cloud Run

Day 4:
Bucket → Pub/Sub → Composer DAG
```

---

## Key Takeaway

The goal is not simply to generate messages.

The goal is to generate messages only for business-relevant events.

In our architecture the landing zone represents new incoming data.

Therefore only files arriving in:

```text
landing/
```

should trigger downstream processing.

Files placed into:

```text
archive/
error/
export/
```

should not start a new ingestion process.

This is the same design principle we will follow later when Cloud Run, Dataform and Composer are added to the architecture.
